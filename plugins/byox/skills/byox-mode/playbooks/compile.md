# Compile

Shared by every source. Start here after an intake playbook ran the learner intake and the stack wizard and wrote a draft `course/course.md`. `B` below is the absolute path of `scripts/byox` next to `SKILL.md`. `C` is the course dir.

1. **Check the intake.** The intake playbook already ran `references/learner-intake.md` and the stack wizard in `references/stack-wizard.md` before writing the outline. The project folders come first: how many codebases the product has, each a folder in `work/` and an entry in `projects:`, because every step the learner reads names them. Check that `plan:`, `stack.choices`, `services:` and `projects:` are in `course.md` and that the learner said yes to the stack and the stand-ins table, then set `stack.confirmed: true`. Ask only what is still open, in one `AskUserQuestion` call. `byox lint` refuses an approved course without `plan:`, `stack.confirmed: true` or `services:`.
2. **Approval.** Show the outline: lessons and steps, the coverage table, the ops track and the dropped list with reasons. Show the batch plan from `plan.batches`: why this batch has this many lessons (time per week), and the themes of the next batches, each added later with `add-lessons.md`. Show the cost: agents (one writer per two lessons when ported, one per lesson otherwise, one reviewer per lesson, plus `byox-teach` per new concept) and rough time (about 15 minutes per lesson of agent time when ported). Revise until the user says yes. Then set `status: approved`.
3. **Scaffold.** `B new C`. It writes lesson stubs, test dirs, verify stubs, `course/.gitignore`, and `course/solution` with an empty commit tagged `base`. For a split course it also makes `work/`, the learner's own folder, with its own git repo. List the concepts in `course.md` whose page does not exist yet in `<vault>/Concepts/`. Each one is written by you in step 8 and checked by that lesson's reviewer.
4. **Diffs.** With an upstream repo, write each step's mentor diff for its writer: `git -C C/course/source/upstream diff <first-sha>^ <last-sha> > C/course/source/diffs/<step>.diff`. Without a repo, skip.
5. **Solution repo, when not ported.** For each step in order, `B tag C <step> --from C/course/source/upstream <last-sha-of-step>`. Ported courses skip this, because the writers build it in step 6.
6. **Brief, then writers.** First write `C/course/brief.md`, once: the course's rules every writer needs and the references cannot know. The projects and their folders, database or resource names writers must use or never touch, real names to keep from the source, shared helpers in `course/support/`, and what each lesson's last step looks like if the course has a pattern for it. Keep it under a page. Then spawn writers. Not ported: one `lesson-writer` per lesson, all at once. Ported: one `lesson-writer` per two consecutive lessons, in order, because lesson N's port starts from lesson N-1's last tag. It writes both, running step 7 on the first before starting the second. Give each writer paths only:
   - the course dir and its lesson ids,
   - `C/course/brief.md`,
   - its lecture files or article section, and its step diffs,
   - `skills/byox-short-read`, `skills/byox-task-writing`, `skills/byox-read-first` (the writer reads each SKILL.md), `references/codecrafters-patterns.md`,
   - `references/course-format.md`, `verify-recipes.md`, `resource-rules.md`, `concept-rubric.md`, and `porting.md` when ported,
   - `<vault>/learner-profile.md` and `<vault>/resource-blocklist.md`,
   - the absolute path of `B`,
   - in port mode, the base tag and the target stack.
7. **Lint and strength.** After each writer returns, run `B lint C --lesson <id>`, `B strength C --lesson <id>` and `B strength C --lesson <id> --regress`. A `regressed` row means this lesson broke an earlier step's check, such as a new login that every page now needs. Fix that earlier test in this session, for example by calling `log_in_as` from `course/support/`, since a writer never edits another lesson. Fix every row before the review.
8. **Deep dives.** For each concept in `course.md` whose owner is this lesson and whose page does not exist yet, run the `byox-teach` skill yourself, in this session. It runs `byox-how` and `byox-why`, which spawn their own agents, and an agent cannot spawn agents, so neither a writer nor a reviewer can do this. Give it the concept, the lesson's chapter of the source, the mentor's diff for the lesson's steps, and the lesson's two resources. It writes `<vault>/Concepts/<slug>.md`. Do it after the lesson's lint and strength pass and before its reviewer starts, while the next writer runs.
9. **Review.** Spawn one `lesson-reviewer` per lesson, never the agent that wrote it. Give it paths only: the course dir, the lesson id, its owned concept pages, the references, the learner profile, the blocklist and `B`. It builds the lesson as a learner from the page alone, scores it, fixes prose in place and writes `course/reviews/<id>.md`. Fix what it reports in tests, verify or the solution in this session, then rerun step 7 for that lesson. A verdict of "back to writer" means a fresh `lesson-writer` with the reviewer's report.
   Never wait on a review to keep writing. In a ported course, as soon as a writer's lessons pass step 7, spawn their reviewers and the next writer in the same message. The next writer builds on the last tag. If a reviewer's fix changes a solution tag, rerun `B strength C --lesson <id> --regress` for every lesson written since. Only a "back to writer" verdict stops the line. Write the next lessons' concept pages while agents run.
10. **Done.** Run `B lint C` on the whole course, with no `--lesson`. Set `status: compiled` only when it exits 0. Lint refuses a released lesson with no `course/reviews/<id>.md`. If you stop early, mark every lesson you did not write or that has no review `building: true` in `course.md` first: lint and the site leave a building lesson out. Then set `status: compiled`. Run `B sync`. Tell the user to start the site with `B site`, or run `start-course.md`.
